📌 1 — Sources officielles et précautions

⚠️ Point de sécurité essentiel

Le projet officiel indique qu’il ne publie pas de tutoriels YouTube officiels ni de binaires précompilés à télécharger. Les Releases officielles servent aux notes de version et ne fournissent pas de fichier .exe. Pour cette raison, ce guide utilise le dépôt officiel et fait produire l’exécutable par ton propre fork et ton propre workflow GitHub Actions.

💡 Pourquoi le fork ?

Un fork est ta propre copie GitHub du dépôt. Il permet de lancer le workflow depuis un dépôt que tu contrôles, tout en gardant un lien avec le dépôt source pour pouvoir le synchroniser ensuite.

✅ Pourquoi synchroniser avant le build ?

Le projet recommande de synchroniser le fork avant chaque compilation afin qu’il contienne les derniers correctifs présents dans le dépôt officiel. Si ton fork est en retard, ton build reproduira le code de cette ancienne version de ton fork, pas les corrections ajoutées depuis.

🚀 4 — Créer son propre WandEnhancer.exe

🎯 Objectif de cette section

À la fin de ces étapes, tu dois avoir téléchargé un ZIP provenant du workflow de ton propre fork et contenant WandEnhancer.exe.

1

Ouvrir le dépôt officiel

ACTION

Ouvre le dépôt officiel : github.com/k1tbyte/Wand-Enhancer.

À VÉRIFIER

La page doit indiquer k1tbyte / Wand-Enhancer. C’est cette page qui sert de référence pour notre procédure ; ne commence pas depuis un miroir, une archive ou un lien vers un exécutable tiers. 

https://github.com/k1tbyte/Wand-Enhancer
Résultat attendu

Tu es bien sur le dépôt public officiel du projet WandEnhancer.

2

Créer ton Fork

ACTION

Depuis la page du dépôt, utilise le bouton Fork, situé en haut à droite de l’interface GitHub.

CE QUE GITHUB TE DEMANDE

L’écran de création du fork permet notamment de choisir le propriétaire du nouveau dépôt et, par défaut, conserve le nom Wand-Enhancer. GitHub peut également proposer une description et l’option Copy the DEFAULT branch only. 

Fork
└── Owner
    └── Ton compte GitHub
└── Repository name
    └── Wand-Enhancer
└── Create fork
💡 Que faut-il choisir ?

Pour ce guide, ton fork doit être créé sous ton compte GitHub et garder le nom Wand-Enhancer, sauf raison particulière de faire autrement. L’option de copie de la branche par défaut concerne les autres branches ; le parcours de ce guide utilise la branche par défaut du dépôt.

POURQUOI CETTE ÉTAPE ?

Le workflow va être exécuté depuis ton dépôt. Ton fork devient donc le point de départ concret de la compilation, tout en restant synchronisable avec le dépôt officiel.

Résultat attendu 
https://github.com/TON_COMPTE/Wand-Enhancer

Le nom exact de ton compte remplace TON_COMPTE. La page doit être présentée comme un fork du dépôt officiel.

3

Synchroniser le Fork

POURQUOI CETTE ÉTAPE EST IMPORTANTE

Ton fork est une copie du dépôt officiel faite à un instant donné. Le projet WandEnhancer recommande d’utiliser Sync fork avant chaque build afin de récupérer les changements plus récents du dépôt source.

Cette étape est particulièrement importante si tu avais déjà créé ton fork auparavant : il peut contenir une version plus ancienne du code alors que le dépôt officiel a reçu des corrections.

ACTION

Depuis la page principale de ton fork, repère le menu Sync fork. GitHub affiche ce menu au-dessus de la liste des fichiers lorsqu’une synchronisation est pertinente. 

Ton fork
└── Sync fork
    └── Update branch

Ouvre Sync fork, examine les informations affichées par GitHub sur les commits provenant du dépôt source, puis utilise Update branch.

⚠️ Ne confonds pas “mon fork existe” et “mon fork est à jour”

Le simple fait de posséder un fork ne garantit pas qu’il contient les dernières corrections. C’est précisément la raison pour laquelle cette synchronisation fait partie du parcours avant chaque build.

✅ Et si GitHub indique que le fork est déjà à jour ?

Rien à mettre à jour : tu peux poursuivre vers Actions.

Cas important — le fork était en retard

Après Update branch, ton fork contient les changements disponibles dans le dépôt officiel. Comme le but du guide est de produire un nouvel EXE correspondant à ce code, c’est à partir de cette version synchronisée que tu dois ensuite lancer le build.

4

Ouvrir GitHub Actions

ACTION

Dans ton fork, ouvre l’onglet Actions. 

TON_COMPTE/Wand-Enhancer
├── Code
├── Issues
├── Pull requests
└── Actions   ← ouvrir ici
⚠️ Attention au dépôt ouvert

Vérifie que tu es bien dans TON_COMPTE/Wand-Enhancer et non revenu sur k1tbyte/Wand-Enhancer. Le build que nous voulons lancer doit appartenir à ton fork.

SI GITHUB TE DEMANDE D’AUTORISER LES WORKFLOWS

Il est possible que GitHub te présente un écran demandant d’activer ou d’autoriser les workflows de ce fork. Lis l’avertissement affiché et active les workflows pour ton dépôt si GitHub te le demande.

Résultat attendu

Une page Actions s’ouvre et une liste de workflows est visible dans la colonne de gauche.

5

Sélectionner « Build executable »

ACTION

Dans la liste des workflows, sélectionne Build executable. 

Actions
└── Build executable   ← sélectionner
CE QUE CELA SIGNIFIE

Tu viens de choisir le workflow spécifiquement prévu par le projet pour construire l’exécutable. Il ne s’agit pas d’une commande que tu dois écrire toi-même : GitHub va exécuter les instructions déjà définies dans le fichier du workflow du dépôt.

Résultat attendu

La page du workflow Build executable affiche un bouton Run workflow lorsqu’il est possible de lancer manuellement cette compilation.

6

Lancer le workflow

ACTION

Clique sur Run workflow. 

Build executable
└── Run workflow
    ├── Branch
    └── Run workflow   ← confirmer
QUELLE BRANCHE CHOISIR ?

Pour le parcours standard, conserve la branche proposée par défaut. Le point important est que cette branche corresponde à celle que tu viens de synchroniser à l’étape précédente.

💡 Pourquoi ne pas changer de branche ?

Le workflow doit construire précisément le code que tu viens de préparer. Choisir une autre branche alors que tu pensais construire la version synchronisée pourrait te faire compiler un contenu différent.

Résultat attendu

Une nouvelle exécution apparaît dans la liste des runs. GitHub attribue un identifiant à cette exécution et commence les étapes de compilation.

7

Suivre et attendre la fin du Build

Ouvre le run que tu viens de lancer et observe son avancement. Le workflow utilise un runner windows-latest et prépare lui-même les outils nécessaires au build.

CE QUE FAIT LE WORKFLOW

Le fichier .github/workflows/build.yml du projet indique notamment qu’il : 

1. récupère le contenu du dépôt
2. prépare pnpm 10.17.0
3. prépare Node.js 22
4. lance ./build.ps1 -Configuration Release
5. charge l’exécutable comme Artifact

Le script de build effectue ensuite plusieurs opérations internes : installation des dépendances du web panel, compilation du web panel, configuration et compilation du composant natif, vérification de ses dépendances runtime, restauration des packages NuGet et compilation de la solution.

RÉSULTAT À ATTENDRE

Le run doit se terminer avec un statut de réussite, généralement affiché en vert, et ses étapes doivent être considérées comme réussies.

🛑 Si le Build échoue

N’ignore pas l’échec et ne le remplace pas par le téléchargement d’un EXE trouvé ailleurs. Ouvre le run, repère l’étape qui a échoué et consulte son journal pour déterminer l’origine du problème. Le dépôt officiel et son historique sont les premières sources à consulter.

8

Ouvrir le Run terminé

Une fois la compilation terminée avec succès, clique sur le run correspondant à ton build. Tu arrives sur la page récapitulative de cette exécution. 

Actions
└── Build executable
    └── Run terminé
        └── Summary   ← page récapitulative
💡 Ne cherche pas l’EXE dans le code source

Le workflow ne modifie pas ton dépôt pour y déposer directement le binaire. Il transmet l’exécutable produit au système d’Artifacts de GitHub, afin que tu puisses le télécharger depuis le run terminé.

9

Dans « Summary », trouver « Artifacts »

Sur la page du run terminé, reste dans Summary. C’est ici que GitHub présente les Artifacts produits par cette exécution. 

Run terminé
└── Summary
    └── Artifacts
        └── WandEnhancer-unsigned
✅ C’est ici que se trouve le résultat

Le workflow actuel du projet publie un Artifact nommé WandEnhancer-unsigned. Le nom peut évoluer dans une future version du projet ; si c’est le cas, cherche l’Artifact associé au workflow Build executable.

10

Télécharger l’Artifact

ACTION

Dans la section Artifacts, sélectionne l’Artifact du build, actuellement nommé WandEnhancer-unsigned.

GitHub télécharge alors une archive contenant le fichier produit par le workflow.

Résultat attendu

Tu obtiens un fichier ZIP correspondant à l’Artifact du run.

🧾 Traçabilité

Conserve éventuellement le ZIP et/ou le lien du run. Ils permettent de retrouver l’exécution précise qui a produit ton fichier si tu dois vérifier ultérieurement la provenance du build.

11

Extraire le ZIP et récupérer WandEnhancer.exe

ACTION

Décompresse le ZIP dans un dossier dédié. Par exemple : 

C:\Tools\WandEnhancer\

Le workflow actuel sélectionne explicitement le fichier : 

WandEnhancer/bin/Release/WandEnhancer.exe

Après extraction de l’Artifact, tu dois retrouver WandEnhancer.exe.

🎉 Objectif atteint

Tu as maintenant un WandEnhancer.exe produit à partir du code de ton fork par ton propre workflow GitHub Actions.

12

Comprendre l’avertissement Windows éventuel

Le README officiel indique que l’Artifact du workflow est unsigned et qu’un exécutable peu répandu peut provoquer une alerte de Windows Defender ou SmartScreen.

⚠️ Une alerte n’est pas une preuve de sécurité ou d’insécurité à elle seule

La vérification importante est la provenance : dépôt officiel → ton fork → ton workflow → Artifact de ton run. Ne désactive pas globalement les protections de Windows simplement pour faire disparaître un avertissement.

🔄 5 — Mettre à jour Wand et reconstruire WandEnhancer

WandEnhancer modifie localement certains éléments de l’installation de Wand. Or Wand continue lui-même d’évoluer. Une mise à jour de Wand peut donc nécessiter une nouvelle version de WandEnhancer pour rester compatible.

✅ La règle pratique

Lorsque Wand reçoit une nouvelle version, vérifie le dépôt officiel de WandEnhancer et son CHANGELOG. Si le projet a publié des correctifs ou une nouvelle version destinée à cette évolution, synchronise ton fork puis reconstruis ton EXE en reprenant la procédure à partir de l’étape Synchroniser le Fork.

🔁 Procédure de reconstruction après une mise à jour de Wand

Mise à jour de Wand
       ↓
Vérifier README / CHANGELOG de WandEnhancer
       ↓
Le projet contient-il des changements/correctifs pertinents ?
       ↓
   Oui / à vérifier
       ↓
Synchroniser le fork
       ↓
Relancer Build executable
       ↓
Récupérer le nouvel Artifact
       ↓
Utiliser le nouvel EXE
💡 Pourquoi le CHANGELOG est utile ici ?

Le projet documente régulièrement des corrections provoquées par les évolutions de Wand. Par exemple, son historique récent mentionne des correctifs du Remote Web Panel pour des builds de Wand plus récents et d’autres ajustements de compatibilité. Le CHANGELOG est donc une source utile pour savoir si une reconstruction est pertinente.

⚠️ Ne reconstruis pas depuis un ancien fork sans le synchroniser

Si ton fork est ancien, tu risques de reconstruire une version dépassée de WandEnhancer alors que le dépôt officiel contient déjà les correctifs nécessaires.

📡 Suivre les nouvelles Releases

Le README recommande de suivre les Releases GitHub via Watch → Custom → Releases. Comme le projet ne fournit plus de binaire officiel à télécharger, cette surveillance sert surtout à savoir quand il est pertinent de resynchroniser ton fork et de relancer le build.

▶️ 6 — Première utilisation et précautions

⚠️ Avant de modifier Wand

Ferme complètement Wand avant les manipulations qui le demandent, vérifie qu’aucun processus pertinent ne reste actif, et conserve une sauvegarde des fichiers importants. Lis les options proposées par WandEnhancer avant d’appliquer un patch.

📁 Organisation simple recommandée

C:\Tools\
└── WandEnhancer\
    └── WandEnhancer.exe

Cette organisation n’est pas imposée par le workflow : elle sert simplement à garder l’EXE construit dans un emplacement identifiable et à séparer le binaire obtenu des autres fichiers téléchargés.

🛡️ À propos des exécutables tiers

Le projet ne prend pas en charge les builds distribués par des tiers. Un exécutable trouvé sur une vidéo, un miroir, une archive ou une pièce jointe inconnue doit être considéré comme non vérifié. La méthode décrite dans ce guide vise précisément à te permettre de produire ton propre binaire.

🧠 7 — Utilisation avancée

Cette partie n’est pas nécessaire pour fabriquer l’EXE. Elle rassemble les fonctions et notions utiles lorsque tu souhaites aller plus loin dans l’utilisation de WandEnhancer.

📱 Remote Web Panel

WandEnhancer inclut un Remote Web Panel permettant de contrôler certaines fonctions depuis un téléphone ou un autre appareil compatible.

Connexion de base

PC avec WandEnhancer
      │
      │ même réseau local
      ▼
Téléphone
      │
      └── scanner le QR code affiché par Connect

Le README indique de placer le PC et le téléphone sur le même réseau Wi-Fi, puis de passer sur le bouton Connect dans la barre supérieure de WandEnhancer et de scanner le QR code affiché.

🌐 Réseau et dépannage

ProblèmeÀ vérifier
La page ne charge pas PC et téléphone sur le même réseau, isolation client/AP du routeur, pare-feu Windows et port TCP 3223.
Le réseau Windows est en Public Le README indique qu’un réseau configuré en Private peut être nécessaire pour certains scénarios locaux.
Accès depuis un autre réseau Utiliser un VPN comme Tailscale ou un outil comparable plutôt que d’exposer directement le port sur Internet.
🚫 Ne pas exposer directement le port 3223 à Internet

Le panneau utilise HTTP sur le port 3223 et n’a pas de code d’appairage. Le README précise qu’une personne pouvant atteindre ce port peut voir le panneau et contrôler le trainer actif. Utilise donc uniquement un LAN/VPN de confiance et n’effectue pas de redirection directe du port vers Internet.

Le protocole du panneau n’inclut pas le bearer token Wand ni les champs liés au chemin d’installation, selon la documentation actuelle du projet.

🧩 Scripts JavaScript personnalisés

Le projet permet d’injecter des scripts JavaScript personnalisés dans le renderer de Wand au moment du patch. Cette fonction réutilise la même injection renderer que le Remote Web Panel et nécessite donc que le patch Remote Web Panel soit activé.

Deux méthodes documentées

Option A — depuis le dialogue de patch
└── Ajouter un ou plusieurs fichiers .js

Option B — depuis le dossier voisin de l’EXE
C:\Tools\WandEnhancer\
├── WandEnhancer.exe
└── renderer-scripts\
    ├── script1.js
    └── script2.js

Ensuite, applique le patch comme d’habitude : les scripts sont intégrés au client et exécutés dans la fenêtre de Wand.

⚙️ Comportement documenté

PointComportement
EnvironnementLe script s’exécute dans le renderer de Wand avec accès au DOM et à require.
ErreursUn script qui lève une erreur est journalisé et n’est pas censé faire planter Wand.
RépétitionUn script peut s’exécuter plusieurs fois pendant un lancement ; les opérations uniques doivent donc être protégées.
API helperWandEnhancer.log(...), WandEnhancer.remoteUrl et WandEnhancer.apiVersion sont disponibles.

Exemple minimal fourni par le projet

if (!globalThis.__helloScriptInstalled) {
  globalThis.__helloScriptInstalled = true;

  WandEnhancer.log("Hello from my custom script!", WandEnhancer.remoteUrl);
  new MutationObserver(() => {
    const dialog = document.querySelector("ux-dialog:not([data-seen])");
    if (dialog) {
      dialog.setAttribute("data-seen", "1");
      WandEnhancer.log("A dialog opened.");
    }
  }).observe(document.documentElement, { childList: true, subtree: true });
}
🛡️ Niveau de privilèges

Le projet indique que ces scripts s’exécutent avec les mêmes privilèges que le client Wand. N’ajoute donc que des scripts dont tu connais la provenance et dont tu comprends le comportement.

🏗️ Comprendre l’architecture

Wand est une application Electron. Le projet WandEnhancer travaille notamment autour des ressources de l’application et de son archive ASAR afin d’appliquer localement ses modifications. 

Wand
├── application
└── resources
    └── app.asar
        ├── JavaScript
        ├── services
        ├── store

Le dépôt contient entre autres un composant .NET/WPF, AsarSharp, un composant natif lié au contournement des fuses ASAR et le code du Remote Web Panel. Cette vue d’ensemble sert surtout à comprendre ce que le build assemble ; elle n’est pas nécessaire pour suivre le parcours GitHub Actions.

🛠️ 8 — Compilation locale avancée

ℹ️ Alternative au workflow GitHub Actions

Cette méthode est optionnelle. Elle sert lorsque tu veux compiler le projet directement sur ton PC, plutôt que de laisser GitHub Actions effectuer le build sur un runner Windows. Pour simplement obtenir un EXE, la méthode principale de ce guide reste plus simple.

🧰 Environnement requis

ComposantRôle
CMakeConfiguration et compilation du composant natif.
Node.js + pnpmInstallation des dépendances et build du web panel.
Visual Studio 2022 ou Build Tools for Visual Studio 2022Fournit MSBuild et l’environnement de compilation requis.
Workload Desktop development with C++Composants C++ nécessaires au build natif.
.NET Framework 4.8 desktop build tools / targeting packÉléments .NET nécessaires à la solution.

📁 Obtenir le code source

Le README demande de cloner le dépôt. Pour une compilation locale cohérente avec le principe de ce guide, tu peux travailler depuis ton fork synchronisé plutôt que depuis un ancien clone non mis à jour. 

TON_COMPTE/
└── Wand-Enhancer/
    ├── build.cmd
    ├── build.ps1
    ├── Wand-Enhancer.sln
    ├── WandEnhancer/
    ├── AsarSharp/
    ├── web-panel/
    └── ...

▶️ Lancer le build

Le point d’entrée documenté est build.cmd, depuis une invite de commandes ou PowerShell, dans le dossier racine du dépôt. 

cd C:\Chemin\Vers\Wand-Enhancer
build.cmd

Le fichier build.cmd appelle build.ps1. Le script PowerShell actuel arrête le build lorsqu’une commande nécessaire est absente et vérifie notamment la présence de cmake, pnpm, Visual Studio/MSBuild et dumpbin. 

build.cmd
   │
   ▼
build.ps1
   ├── vérifier cmake / pnpm / Visual Studio / MSBuild / dumpbin
   ├── pnpm install --frozen-lockfile
   ├── pnpm run build
   ├── CMake configure
   ├── CMake build
   ├── vérifier les dépendances de version.dll
   ├── MSBuild Restore
   └── MSBuild Build
⚠️ Une erreur « Required command not found in PATH »

Le script actuel utilise le PATH pour résoudre notamment cmake et pnpm. Il résout également Visual Studio/MSBuild avec vswhere. Une erreur indiquant qu’une commande nécessaire est introuvable signifie généralement que l’outil correspondant n’est pas installé ou n’est pas accessible depuis l’environnement courant.

🔍 Pourquoi la compilation locale est plus complexe ?

GitHub Actions masque une grande partie de la préparation en installant les outils demandés par le workflow sur son runner. En local, c’est toi qui dois fournir cet environnement et t’assurer que toutes les commandes nécessaires sont disponibles. C’est la raison pour laquelle cette méthode est classée « avancée » ici.

SymptômeVérifications prioritaires
Je ne trouve pas l’Artifact Vérifie que le run est terminé, ouvre la page du run puis Summary et cherche Artifacts. Le workflow actuel produit un Artifact nommé WandEnhancer-unsigned.
Le build est rouge Ouvre le run et identifie l’étape en échec. Lis son journal avant de relancer inutilement le build.

📚 Quand le problème n’est pas couvert ici

Commence par le README et le CHANGELOG officiels. Pour un échec GitHub Actions, le journal du run reste généralement la première information concrète à examiner.
